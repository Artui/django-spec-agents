    Child sessions¶

    The toolset, the lineage a child carries, the report frame and the types around them. See Child sessions for the narrative. Each imports from its own module under django_spec_agents.child_sessions, except ChildLineageRecord, which a Conversation holds and so lives under django_spec_agents.persistence.types.

    ChildSessionsToolset¶

    ChildSessionsToolset ¶

    Bases: FunctionToolset[Any]

    Tools to start, list, message, answer and cancel child sessions, and for a child to ask.

    start_session starts a child on one of agents (an id to a description the model reads) through runner, as the run's own user, and returns a ChildSessionReceipt naming its thread. list_tasks, message_task, answer_task and cancel_task keep upstream TaskControl's names, so a mount carrying both is refused by pydantic-ai's duplicate-name check; ask_parent is offered in a child only, and parks it as waiting on a question.

    Needs the [harness] extra. Starts run one at a time, so each reads the index after the last; an anonymous run is refused. A child carries a ChildLineage and, with spend, two SpendLimits. Each limit in limits refuses a start with a ChildSessionRefusal.

    The run's thread is ctx.conversation_id and its request is ctx.deps.call_context["request"], as a transport's default deps put it there.

    ChildLineage¶

    ChildLineage dataclass ¶

    Bases: AbstractCapability[Any]

    Where a child run sits in its tree, and the tools its parent had: composed into the child.

    depth counts from the root thread at 0. The child sees only the tools named in tools beside the child-session tools, so it is never wider than its parent, and a tool named in gated asks for approval in the child as it did in the parent, on top of the child mount's own guards.

    ChildReport¶

    ChildReport dataclass ¶

    Bases: AbstractCapability[Any]

    Enqueues a child run's report on its parent's inbound queue when the run settles.

    Needs [harness], checked when built. A run that parks, or is cancelled before its deadline, sends nothing; a failed enqueue is logged and never replaces the run's own.

    child_lineage_for¶

    child_lineage_for ¶

    child_lineage_for(
    conversation: Conversation,
    *,
    agent_id: str,
    owner: str,
    queue: InboundQueue,
    spend: ChildSessionSpend | None = None,
) -> list[AbstractCapability[Any]]

    The capabilities a run of a child's thread composes, rebuilt from its stored lineage.

    The same ones start_session gave its first run: the parent's tool bounds, the report on settle, and, with spend, the tree and day budgets. agent_id is the child's mount and owner its user's id; a thread with no stored lineage gets none.

    ChildLineageRecord¶

    ChildLineageRecord dataclass ¶

    What a child thread keeps of its lineage, so a later run of it rebuilds the same bounds.

    root and depth place it in its tree; tools and gated are its parent's tools and the ones the parent gated, as sorted lists so the record crosses a queue.

    report_frame¶

    report_frame ¶

    report_frame(
    child: ThreadRef, *, agent_id: str, output: str, outcome: ReportOutcome = "ok"
) -> UserPromptPart

    A settled child's report to its parent, framed as upstream's <task_output> data.

    Built through pydantic-ai-harness's public DelegationTask.report(), so the child's output never enters system voice and cannot close its own frame. The task id is the child's thread id. Needs the [harness] extra.

    ChildSessionReceipt¶

    ChildSessionReceipt dataclass ¶

    What start_session returns as its tool result: the child's (agent_id, thread_id).

    The tool result is the part of a delegation that persists, so a client finds the child's thread here after a reload.

    ChildSession¶

    ChildSession dataclass ¶

    A child session as its parent sees it: the child's thread and where its runs stand.

    A child is live while it runs or waits, since a parked child still holds its slot.

    live property ¶

    live: bool

    Whether the child counts against the running limits: it runs, or it waits.

    ChildSessionIndex¶

    ChildSessionIndex ¶

    Bases: Protocol

    Finds child sessions, for the limits and for cancel: the two questions no store answers.

    Keyed like a ConversationStore, by the owner each method resolves from its request. A child's link to its parent is the parent its conversation stores, in any scope, so an index reads those links and the children's run status beside them. A child must be listed from the moment HeadlessRunner.start returns, or two starts in a row both pass the per-thread limit.

    ChildSessionLimits¶

    ChildSessionLimits dataclass ¶

    How far child sessions may go: their depth, how many run at once, and each run's deadline.

    timeout is each child run's deadline in seconds, required as a routine's is. A root thread is depth 0, so the default max_depth of 2 allows a child and a grandchild. The running limits count children that run or wait: per parent thread, and per user across every thread.

    ChildSessionSpend¶

    ChildSessionSpend dataclass ¶

    The spend budgets every child run carries, as pydantic-ai-harness SpendLimits.

    tree_usd caps the whole tree under one root thread, for all time; day_usd caps one user's children per day. store is the harness SpendStore the counters live in, Any because the harness is optional: it must be one every worker shares, never an in-memory store. None for a budget counts and never stops.
