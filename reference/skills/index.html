    Skills¶

    The stored-skill model, its policy and the functions over them. See User skills for the narrative. Everything here imports from django_spec_agents.skills.

    AbstractSkill¶

    AbstractSkill ¶

    Bases: Model

    A user-written skill; the consumer subclasses it with its tenant relation and policy.

    The two flags mirror SKILL.md's user-invocable and disable-model-invocation.

    ReservedSkillNames¶

    ReservedSkillNames ¶

    Bases: Protocol

    The optional hook a SkillPolicy adds to keep the names its code-registered skills hold from being taken by a stored one.

    A policy that defines reserved_names has create_skill, update_skill and every write through them, the skill tools and an editor endpoint alike, refuse a stored skill named like a reserved one. A policy without it reserves nothing.

    reserved_names ¶

    reserved_names(request: HttpRequest) -> Collection[str]

    The names no stored skill may take for this caller.

    SkillScanning¶

    SkillScanning ¶

    Bases: Protocol

    The optional hook a SkillPolicy adds to scan user-authored skills, with pydantic-ai-harness's ArtifactScanner or one of its shape.

    A policy with a scanner attribute has create_skill, update_skill and import_skill_md refuse a draft whose description or body the scanner flags, with InvalidSkillError naming the field, and has a flagged stored row left out of what StoredSkills offers a run and what the list_skills tool lists. A policy without it, or whose scanner is None, scans nothing.

    SkillScoping¶

    SkillScoping ¶

    Bases: Protocol, Generic[SkillT]

    The optional hook a SkillPolicy adds to say whether a skill is the caller's own or one shared with them.

    A policy that defines scope lets a transport label each skill it shows: the django-ag-ui skill editor, from 0.91.0, carries it as the entry's scope key. scope returns "personal" for a skill in the caller's own scope and "shared" for one another scope holds (a tenant's or a company's). A policy without the method labels nothing, and a transport leaves the key out. It is a separate protocol because a Protocol has no optional members: adding scope to SkillPolicy would break every policy written before it.

    scope ¶

    scope(request: HttpRequest, skill: SkillT) -> SkillScope

    "personal" when skill is in the caller's own scope, else "shared".

    The caller's enabled skills, one per name: the first policy.visible yields wins.

    A disabled skill shadows nothing, so disabling a personal skill brings back the company one of the same name. The list stops at MAX_VISIBLE_SKILLS, in the policy's order.

    create_skill¶

    create_skill ¶

    create_skill ¶

    create_skill(
    policy: SkillPolicy[SkillT], request: HttpRequest, draft: SkillDraft
) -> SkillT

    Create a skill from draft in the scope policy.new_skill gives, if can_write admits it.

    Raises InvalidSkillError for a broken rule, SkillLimitError when the caller already sees MAX_VISIBLE_SKILLS enabled skills, and SkillWriteRefusedError when the policy refuses. A name the policy reserves through ReservedSkillNames, and a description or body its SkillScanning scanner flags, are an InvalidSkillError.

    update_skill¶

    update_skill ¶

    update_skill ¶

    update_skill(
    policy: SkillPolicy[SkillT], request: HttpRequest, skill: SkillT, draft: SkillDraft
) -> SkillT

    Replace skill's name, description, body and flags with draft's, if can_write admits it.

    can_write is asked twice, of the row as stored and of the result, so a policy can refuse both touching a skill and a change to it. Raises InvalidSkillError for a broken rule and SkillWriteRefusedError when the policy refuses; a refused update leaves both the row and skill as they were. A rename to a name the policy reserves through ReservedSkillNames is an InvalidSkillError; a skill keeping a name reserved since it was stored is not. So is a description or body the policy's SkillScanning scanner flags; the stored row is not scanned.

    enable_skill ¶

    enable_skill(
    policy: SkillPolicy[SkillT], request: HttpRequest, skill: SkillT

    Turn skill back on if can_write admits the row and the result; a refusal changes nothing.

    Raises SkillLimitError when the caller already sees MAX_VISIBLE_SKILLS enabled skills, as create_skill does, and SkillWriteRefusedError when the policy refuses.

    StoredSkills¶

    StoredSkills ¶

    Bases: AbstractCapability[Any]

    The caller's stored skills, one deferred capability each, read per run: pass it in a run's capabilities=. With authoring=True the run also gets build_skill_tools and the bundled create-skill skill, which a visible stored skill of that name shadows.

    export_skill_md ¶

    skill as a SKILL.md, the four frontmatter fields the harness reads and the body.

    parse_skill_md reads it back to the same fields, and the harness's Skills loads it from a directory named after the skill. enabled and the scope are not part of the file.

    parse_skill_md¶

    parse_skill_md ¶

    parse_skill_md ¶

    parse_skill_md(text: str) -> SkillDraft

    Read a SKILL.md into a cleaned SkillDraft; raises InvalidSkillError if it cannot.

    The frontmatter is a strict subset of YAML: one-line entries for name, description, user-invocable and disable-model-invocation, and nothing else, so no field is dropped.
