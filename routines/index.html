    Routines¶

    A routine is a stored prompt for one agent, a schedule, and the user it runs as: "every weekday at 8, run /what-is-on and tell me what is overdue". The package gives you the model's fields, a policy protocol, the schedule vocabulary, the next-firing computation, and the functions that write a routine. You bring the concrete model, its tenant relation, its migration and the policy. No concrete routine model ships in the package, and no default policy.

    This page covers the storage, the rules and the sweep that fires a routine on schedule. The spec a firing runs and showing its thread are later pieces.

    The model¶

    Subclass AbstractRoutine and add whatever scopes a routine in your project:

    from django.db import models

from django_spec_agents.routines import AbstractRoutine, RoutinePolicy


class Routine(AbstractRoutine):
    team = models.ForeignKey("teams.Team", on_delete=models.CASCADE)

    @classmethod
    def routine_policy(cls) -> RoutinePolicy["Routine"]:
        return OwnRoutinesPolicy()


class OwnRoutinesPolicy:
    def visible(self, request):
        return Routine.objects.filter(principal=request.user)

    def can_write(self, request, routine):
        return routine.principal_id == request.user.pk

    def can_run(self, principal, routine):
        return principal.is_active and routine.team.members.filter(pk=principal.pk).exists()

    def new_routine(self, request):
        return Routine(team=request.user.team)
    Field Meaning
    name What the person calls it, at most 120 characters
    agent_id The agent the routine runs
    prompt The message each firing sends, at most 20,000 characters
    schedule The schedule, as the JSON schedule_to_json writes; read it with get_schedule()
    timezone The IANA zone the schedule's wall times are read in; get_timezone() loads it
    principal The user each firing runs as: always the user who created the routine
    enabled, paused_reason Off means it does not fire; a pause by the system says why
    preapproved_tools The tools a firing may call without parking, each with its pinned flag
    next_fire_at The next firing, in UTC, indexed; None while the routine is disabled
    last_run_id The queue's run id for the last firing
    last_thread_id The thread the last firing ran into
    created_by, created_at, updated_at Who wrote it, and when

    The policy¶

    RoutinePolicy is four methods:

    • visible(request) returns every routine the caller may see, disabled ones too.
    • can_write(request, routine) decides whether the caller may save routine, a new unsaved one or an existing row.
    • can_run(principal, routine) decides whether routine may fire now as its principal. A firing has no request, so it is asked with the user alone.
    • new_routine(request) returns the unsaved routine a create writes to, with its scope already set.

    The schedule¶

    The vocabulary is closed, and there are no cron strings:

    • WeeklySchedule(weekdays, at) fires on each weekday (0 is Monday, 6 is Sunday) at the wall time at, to the minute, in the routine's timezone.
    • IntervalSchedule(every_hours) fires every N hours of elapsed time, whatever the timezone's clock changes do. An interval shorter than MIN_ROUTINE_INTERVAL, an hour, or longer than MAX_ROUTINE_INTERVAL, 366 days, is refused.

    parse_schedule(data) reads a schedule from its JSON, {"kind": "weekly", "weekdays": [0, 1, 2, 3, 4], "at": "08:00"} or {"kind": "interval", "every_hours": 6}, and raises InvalidRoutineError for anything else. schedule_to_json writes it back.

    next_fire_at(schedule, timezone, after) returns the first firing strictly after after, in UTC. A weekly wall time a DST change skips fires shifted by the gap, so 02:30 on a spring-forward night fires at 03:30. A wall time it repeats fires once, at its first occurrence. An interval adds its hours to after, so pass the firing just claimed rather than the clock, or every late sweep pushes the cadence later.

    Writing¶

    from datetime import time

from django_spec_agents.routines import RoutineDraft, WeeklySchedule, create_routine

policy = Routine.routine_policy()
create_routine(
    policy,
    request,
    RoutineDraft(
        name="Overdue digest",
        agent_id="assistant",
        prompt="/what-is-on: tell me what is overdue",
        schedule=WeeklySchedule(weekdays=frozenset(range(5)), at=time(8, 0)),
        timezone="Europe/London",
        preapproved_tools=("archive_invoice",),
    ),
    guard=agent_guard,
    tool_defs=agent_tool_defs,
)
    • create_routine makes the caller the principal and created_by, and refuses an anonymous caller with RoutineWriteRefusedError. It raises InvalidRoutineError once the caller holds MAX_ROUTINES_PER_USER (25) routines, counted on the model by principal, disabled ones included. The count is read before the insert, so two creates racing at the cap can both pass it; a host that needs a hard cap holds a lock around the call.
    • update_routine replaces the fields but never the principal, whoever edits. next_fire_at moves only when the schedule, the timezone or enabled changes, so an edit to the prompt keeps an interval's cadence. An enabled routine carries no paused_reason, so turning one back on clears it.
    • Both ask can_write, and raise RoutineWriteRefusedError when the policy refuses. An update asks twice, once about the row as stored and once about the result, and a refusal leaves the instance it was given as it was. A blank name, agent or prompt, an oversized one, and a timezone zoneinfo cannot load raise InvalidRoutineError.

    Pre-approved tools¶

    A routine's firings run with no one watching, so a gated tool call parks the thread unless the routine pre-approved the tool. The grant is made when the routine is created or edited, and that edit is where a person approves it.

    The grant pins each tool's flag. pin_preapproved_tools(guard, tool_defs, names) asks the agent's ToolGuard.requires_approval about each named definition and records the answer as destructive. A name none of tool_defs carries raises InvalidRoutineError, so a typo is never recorded as a grant. create_routine and update_routine pin through it, checking every granted name against the agent's tools on each write. While the agent stays the same, an update keeps the flag already pinned for a tool the routine held, so an unrelated edit never re-approves a tool declared destructive since. Moving the routine to another agent pins every tool afresh against that agent's guard. A tool dropped from the list is revoked, and pins afresh if named again.

    preapproved_exempt(routine) returns the names a firing's guard exempts: only the tools that were gated when granted. A tool granted while ungated and declared destructive later is not among them, so its call parks. Passed to GrantedApprovals with f"routine:{routine.pk}", the same names are approved in the run and each call's result and audit record carry the routine as answered_by.

    Firing due routines¶

    The package ships no schedule of its own. Your project runs the run_due_routines management command every minute or so, from cron, a systemd timer or its task scheduler, and each run fires the routines that have come due since the last. It needs django_spec_agents in INSTALLED_APPS.

    The command sweeps every installed routine model whose routine_sweep() returns a RoutineSweep; a model that keeps the default None is left alone:

    from django_spec_agents.routines import AbstractRoutine, RoutineSweep


class Routine(AbstractRoutine):
    ...

    @classmethod
    def routine_sweep(cls) -> RoutineSweep:
        return RoutineSweep(queue=firing_queue, spec_name="run_routine")
    • queue is your FiringQueue, the same seam a queued headless run goes through, filled from django-spec-tasks or another task queue.
    • spec_name is the name your queue's registry holds the firing spec under. The sweep enqueues it as the routine's principal with {"routine_id": <pk>, "thread_id": <id>}, a fresh thread id per firing, which the spec runs into.
    • grace is how late a missed firing may still run. Leave it None for one schedule period, measured from the firing that was missed: a day for a daily routine, three days for a weekday routine's Friday firing.

    due_routines(model, sweep, now=None, limit=100) is what the command calls, for a project that would rather call it from its own task. It claims the due rows in one query on the indexed next_fire_at, with select_for_update(skip_locked=True), and moves each to its next firing in the transaction that enqueues it. Two sweeps that overlap therefore fire a routine once: the second passes over the rows the first holds. Run it on a database that honours skip_locked, such as PostgreSQL; SQLite ignores the lock.

    For each claimed routine, in this order:

    The routine The sweep
    Its last firing lapsed: the worker died, or the principal or the spec went away Pauses it: enabled off, next_fire_at and last_run_id cleared, paused_reason naming the run
    It is later than its grace, say after downtime Skips it, logs it, and counts it as missed
    Its last firing is still pending, or its thread still waits (below) Skips it
    The policy's can_run refuses its principal Pauses it with that reason
    Otherwise Enqueues the firing with a fresh thread id, and stores the run id as last_run_id and the thread as last_thread_id

    However late the sweep, next_fire_at moves to the first firing after now, stepped from the one claimed, so an outage fires a missed routine at most once and an interval keeps its cadence. A routine whose handling raises is rolled back, logged and left for the next sweep, and the others go on. The command prints one line per model, and due_routines returns the same counts as a SweepResult of primary keys.

    A firing parked on a person¶

    A firing that reaches a gated tool it was not granted parks its thread until someone answers the approval card. Starting the next firing beside it would leave two threads waiting on the same question, so the sweep asks the model first:

    from asgiref.sync import async_to_sync
from django.http import HttpRequest

from django_spec_agents import ThreadRunStatus
from django_spec_agents.contrib.store.default_run_store import DefaultRunStore


class Routine(AbstractRoutine):
    ...

    @classmethod
    def thread_waits(cls, thread_id, principal) -> bool:
        request = HttpRequest()
        request.user = principal
        state = async_to_sync(DefaultRunStore().get)(thread_id, request=request)
        return state is not None and state.status == ThreadRunStatus.WAITING

    thread_waits(thread_id, principal) is asked about last_thread_id, as the routine's principal, and a True skips this firing. The hook is synchronous and the run store is async and scoped by the owner a request carries, so it builds a request for the principal and bridges the call. The default returns False, so a project that does not fill it fires on schedule whatever its last thread is doing.

    Finding the model, and refusing one with no policy at startup¶

    There is no setting naming the routine model: the core reads no Django settings. Your code holds the model and its policy, and passes the policy to every function above and to whatever transport serves routines, as a constructor argument.

    Add the package's opt-in app to INSTALLED_APPS, as for user skills. Its system check walks Django's app registry: every installed concrete model that subclasses AbstractRoutine must bring a policy, so manage.py check, runserver and migrate fail otherwise:

    Id When
    django_spec_agents.E002 An installed AbstractRoutine subclass's routine_policy() returns None, which is AbstractRoutine's default

    An abstract layer between AbstractRoutine and your model is not checked, because it has no table. Import django_spec_agents.routines once the app registry is ready, because it defines an abstract model.
